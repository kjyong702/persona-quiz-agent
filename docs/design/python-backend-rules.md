# Python 백엔드 설계 규칙

> 신규 프로젝트 설계 시 AI 코딩 도구에 컨텍스트로 주는 문서. 이 리포의 CLAUDE.md Part 2는 이 규칙의 적용본이다.

## 왜 이 문서인가

AI 도구가 회사(개인) 스타일과 다른 코드를 내는 원인은 대부분 도구 성능이 아니라 컨텍스트 부족이다. 매번 코드베이스 전체를 읽히는 대신 규칙을 짧은 문서로 고정해 두면 토큰 소모가 줄고 결과물이 일관된다. 규칙이 늘거나 바뀌면 이 문서를 갱신한다.

## 레이어링

- routers / services / repositories / schemas / core 5개 레이어, 의존은 단방향
- 라우터는 얇게: 스키마 검증과 서비스 호출만. 비즈니스 로직이 라우터에 들어가면 실패
- 외부 API 호출(LLM, 임베딩 등)은 core의 클라이언트 모듈로 감싼다 — 재시도, 폴백, 타임아웃을 한 곳에서 관리하고 서비스 테스트에서 목 대체가 쉬워진다

## DB

- 테이블 복수형 snake_case, PK `id`, FK `<단수형>_id`, 생성 시각 `created_at` 기본 포함
- JSON 컬럼은 "목록인데 별도 테이블로 뽑을 만큼 조회 패턴이 없을 때"만 (예: 기대 정답 표현 목록)
- 판정/추론 결과를 저장할 때는 결과값만이 아니라 **판정 경로와 근거 수치를 함께 남긴다** (튜닝과 평가의 원천 데이터)

## API

- 공통 응답 래퍼 `{ data, error }`, 에러는 `{ code, message }` 상수 코드
- 엔드포인트는 리소스 중심 복수형, 행위는 하위 경로 (POST /sessions/{id}/answer)
- 응답에 내부 구현 노출 금지 (프롬프트 원문, 모델명 등은 응답이 아니라 로그로)

## LLM 연동

- 프롬프트는 코드에 문자열로 박지 않고 버전 붙은 파일로 관리 (평가 파이프라인의 대상이 되도록)
- LLM 호출에는 항상 실패 경로를 설계한다: 폴백 판정, 타임아웃, 재시도 상한
- 비용이 걸린 판정은 "LLM을 언제 부르지 않을 수 있는가"부터 설계한다 (임베딩 1차 판정이 그 답)

## 테스트

- 서비스 레이어 단위 테스트가 기본, 외부 API는 목
- 프롬프트 품질은 단위 테스트가 아니라 평가 도구(promptfoo)로 검증 — 둘을 섞지 않는다
