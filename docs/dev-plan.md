**Phase가 끝나면 `docs/notes/build-log.md`에 그 단계에서 마주친 것을 덧붙인다.**
실제로 터진 것과 미리 막은 것을 구분해서 적는다. 섞으면 나중에 겪지 않은 일을
겪었다고 착각하게 되고, 그러면 기록이 쓸모를 잃는다.

## 개발 도구도 산출물이다 — `.claude/skills/`

이 프로젝트는 **문서 주도 개발 프로세스를 보이는 것**이 목적 중 하나다. 그렇다면 **그 프로세스를 돕는 도구
자체도 리포에 남는 것이 맞다.**

개발하면서 실제로 쓴 Claude Code skill을 `.claude/skills/`에 커밋한다. 후보는 이 프로젝트 안에서 나온다.

| 스킬 | 하는 일 |
|---|---|
| `phase-commit` | `dev-plan.md`의 Phase를 읽고 커밋 메시지 규격에 맞춰 커밋 |
| `doc-sync` | 코드를 고쳤을 때 `api-spec.md`, `db-schema.md`와 어긋나는지 검사 |
| `eval-run` | promptfoo를 돌리고 결과를 `eval/README.md`에 반영 |

> **원칙**: 만들기 위해 만들지 않는다. **개발 중에 실제로 반복된 작업만 스킬로 승격**시키고,
> 그 스킬이 왜 필요했는지를 스킬 문서에 남긴다. 쓰지 않은 스킬은 커밋하지 않는다.

### 판정 기준의 재현성 (Phase 3에 포함)

판정이 흔들리지 않으려면 비교 축이 고정되어야 한다. 아래를 구현 요건으로 못 박는다.

- **앵커 고정**: 기대 정답 키워드를 판정의 고정 축(앵커)으로 두고, 사용자의 자유 서술 답변을 그 앵커와의 유사도로 환산해 판정한다. 자유 텍스트끼리 직접 비교하지 않는다
- **정규화 렌더링**: 임베딩에 넣는 문자열은 값만 이어붙이지 않고 항상 같은 템플릿으로 만든다. 템플릿을 바꾸면 기존 벡터와 비교가 불가능하므로 템플릿도 버전 관리 대상이다
- **버전 기록**: 판정 레코드에 임베딩 모델 ID와 템플릿 버전을 함께 남긴다. 모델을 바꾸면 기존 유사도 값이 무효라는 것을 데이터로 보일 수 있어야 한다
- **임계값은 상대 기준 병행**: 절대 임계값 하나만 두지 않는다. 최소 하한은 유지하되 경계 구간은 Phase 5 평가로 정한다

## Phase 3.5. 동시성과 레이트 리밋 대응

LLM 호출은 외부 유료 API에 의존하므로 병목이 우리 서버가 아니라 제공사 쿼터에 있다. 서버를 늘려서 푸는 문제가 아니라 나가는 흐름을 한도에 맞추는 문제로 다룬다.

- **흐름 정형**: `asyncio.Semaphore`로 동시 인플라이트 상한, 토큰 버킷 레이트 리미터로 분당 호출량 제한
- **실패 흡수**: tenacity 기반 지수 백오프와 지터. **응답의 Retry-After 헤더를 존중**하고 고정 백오프로 덮어쓰지 않는다
- **재현 실험**: 동시 N개 답변을 제출하는 부하 스크립트를 작성해 429를 의도적으로 발생시킨다
- **측정 기록**: 대응 적용 전후로 성공률, 429 발생 수, p95 지연을 기록해 `docs/notes/concurrency.md`에 남긴다. 수치 없는 개선 주장을 하지 않는다
- **큐 도입 판단**: 작업 큐(arq 등) 도입 여부는 위 측정 결과로 결정한다. 세마포어로 충분하면 넣지 않고, 넣지 않은 이유를 기록한다
- 단위 테스트: 429 응답을 목으로 주입해 재시도 횟수와 백오프 동작을 검증

### 프롬프트 레이아웃과 캐싱 (Phase 4에 포함)

- 시스템 프롬프트를 **공통 프리픽스와 개인 델타로 분리**한다. 여러 세션이 공유하는 고정 지시문을 앞에, 페르소나별 및 세션별 변동분을 뒤에 배치한다
- 앞 구간이 바이트 단위로 동일해야 제공사 프롬프트 캐싱이 걸린다. 프리픽스 안에 세션 ID나 타임스탬프 같은 변동 값을 넣지 않는다
- 응답 메타의 캐시 적중 토큰 수를 로깅해 **분리 전후 입력 토큰 비용을 비교 기록**한다

## Phase 5. 평가 파이프라인 (promptfoo)

- eval/dataset/: 라벨링 답변 데이터셋 (문제별 정답 변형, 오답, 애매 케이스 각각 포함)
- 판정 정확도 평가: 임계값 조합별 정확도와 LLM 호출 비율 비교 -> 기본 임계값 확정, 결과를 eval/README.md에 기록
- **패러프레이즈 불변성 점검**: 같은 뜻을 다르게 쓴 문장 쌍, 길이만 다른 쌍을 넣어 유사도가 유지되는지 확인한다. 정규화 템플릿 적용 전후로 같은 셋을 돌려 개선 여부를 수치로 남긴다
- 페르소나 회귀 평가: 프롬프트 버전별 응답이 말투 유지/정답 유출 금지 규칙을 지키는지 assertion

## Phase 6. 배포 구성

로컬 실행만으로는 이 서버의 운영 특성이 드러나지 않는다. 배포 단위가 코드 하나가 아니라는 것을 구성으로 보인다.

- **설정 분리**: 모델 ID, 임계값, 프롬프트를 코드에서 분리한다. 모델은 별칭이 아니라 **날짜가 박힌 스냅샷 ID로 고정**하고 교체 시 평가를 다시 돌린다
- **시크릿 외부화**: API 키를 리포와 이미지에 넣지 않는다. `.env.example`만 커밋하고 실제 주입 경로를 README에 문서화
- **시크릿 회전**: 지금은 OpenAI 클라이언트를 첫 호출에 만들어 프로세스 수명 내내 재사용한다. 키를 부팅 시 한 번 읽고 캐시하는 구조라 키를 회전시켜도 재배포 전까지 반영되지 않는다. TTL을 둔 재생성 경로를 넣는다 (Phase 3에서 만든 `app/core/embedding.py`, `app/core/llm.py`의 `_get_client`)
- **타임아웃 체인**: LLM 호출이 수십 초 걸릴 수 있으므로 애플리케이션 타임아웃을 앞단보다 짧게 두어 서버가 먼저 끊게 한다. 리버스 프록시를 둘 경우 버퍼링 해제와 read timeout 상향을 함께 문서화
- Dockerfile과 compose 구성, 헬스체크 엔드포인트
- 커밋: `chore: 배포 구성 (설정 분리, 시크릿 외부화, 타임아웃 체인)`
