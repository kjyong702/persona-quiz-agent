# 빌드 로그

개발하면서 마주친 것들. Phase가 끝날 때마다 덧붙인다.

**성격을 구분해서 적는다.** 실제로 터진 것과 미리 막은 것을 섞으면 나중에
"내가 이걸 겪었다"고 착각하게 되고, 그건 기록의 가치를 없앤다.

| 표시 | 뜻 |
|---|---|
| 🔴 **터짐** | 실제로 실행이 실패했거나 멈췄고, 원인을 찾아 고쳤다 |
| 🟡 **예방** | 터지기 전에 알아채고 그 자리에 검증을 박았다 |
| 🔵 **구멍** | 문서나 설계를 읽다가 정해지지 않은 것을 발견했다 |
| ⚪ **감사** | 코드를 짜다 마주친 것이 아니라 **사후 감사에서 찾아낸 것** |

> ⚪를 따로 둔 이유: 나머지 셋은 개발 중에 몸으로 부딪힌 것이고 ⚪는 다 만든 뒤에
> 훑어서 찾은 것이다. 둘을 섞으면 겪지 않은 일을 겪었다고 말하게 된다.
> **가치가 낮다는 뜻이 아니라 출처가 다르다는 뜻이다.**

## 🔴 토큰 버킷이 무한 루프에 빠졌다 (Phase 3.5)

### 무슨 일이 있었나

레이트 리미터 테스트를 돌렸더니 **테스트 실행이 끝나지 않았다.** 타임아웃도 없이
그냥 멈춰 있었다. 테스트를 하나씩 분리해서 돌려 범인을 찾았다.

```python
clock.now += 3600.0          # 한 시간 방치했다고 가정
for _ in range(10):
    await bucket.acquire()   # 여기까지는 통과
await bucket.acquire()       # 여기서 영원히 안 돌아온다
```

### 왜 그랬나

두 원인이 겹쳤다.

**1. 큰 수끼리 빼면 정밀도가 떨어진다.**

```
3600.1 - 3600.0 = 0.09999999999990905
```

`3600.1`은 float64로 정확히 표현되지 않는다. 1초를 기다려도(초당 10토큰이면)
토큰이 `0.9999999999990905`밖에 안 차서 `>= 1.0` 검사를 통과하지 못한다.

**2. 그러면 다시 계산한 대기 시간이 너무 짧아진다.**

부족분이 `9.09e-13`이므로 대기 시간은 `9.09e-14초`. 그런데 3600 근처에서
float64의 최소 간격(ULP)은 약 `4.5e-13`이다. **자고 일어나도 시계 값이 안 바뀐다.**
그러면 경과 시간이 0이고, 토큰도 그대로고, 대기 시간도 그대로다. 영원히 반복된다.

### 어떻게 막았나

```python
if self._tokens >= 1.0 - _TOKEN_EPSILON:      # 오차만큼 여유
    ...
sleep_for = max(_MIN_SLEEP, deficit / rate)   # 최소 대기로 진행 보장
```

두 개가 각각 다른 원인을 막는다. 오차 허용치는 1번을, 최소 대기는 2번을 막는다.
**하나만 넣으면 다른 조건에서 다시 멈춘다.**

### 배운 것

`time.monotonic()`은 **부팅 이후 계속 커지는 값**이다. 개발 중에는 작은 숫자라
아무 문제가 없다가, **오래 켜둔 서버에서 조용히 재현된다.** 시각을 다루는 코드는
"값이 클 때"를 따로 생각해야 한다.

그리고 `while True` 루프 안에서 대기 시간을 계산할 때는 **그 값이 0에 수렴할 수
있는가**를 봐야 한다. 진행을 보장하는 하한이 없으면 라이브락이 된다.

### 재발 방지

`test_bucket_makes_progress_at_any_clock_offset` — 시작 시각을 0, 3600, 86400,
1000000으로 바꿔가며 돌린다. **끝나는 것 자체가 단정이다.**

## 🔴 잔액 소진이 429로 와서 재시도를 탔다 (Phase 3.5)

### 무슨 일이 있었나

API 키를 처음 넣고 시드를 돌렸더니 앵커 적재가 실패했다.

```
Error code: 429 - {'error': {'message': 'You exceeded your current quota...',
                             'type': 'insufficient_quota',
                             'code': 'insufficient_quota'}}
```

키는 유효한데 **결제 잔액이 0**이었다. 문제는 그다음이다. 이 응답이
`RateLimitError`(429)로 오기 때문에 **우리 재시도 로직이 재시도 대상으로 판단했다.**
결제하기 전에는 영원히 성공할 수 없는 호출을 백오프까지 밟아가며 4번 걸었다.

실제 응답을 확인한 결과는 이랬다.

| 항목 | 값 |
|---|---|
| 예외 클래스 | `RateLimitError` |
| status_code | 429 |
| code | `insufficient_quota` |
| retry-after 헤더 | 없음 |

### 왜 문제인가

두 가지다.

**1. 무의미한 대기.** 사용자는 절대 성공하지 않을 호출을 기다린다.

**2. 측정이 거짓말을 한다.** 이게 더 나쁘다. Phase 3.5의 부하 실험은
"429가 몇 번 났고 대응이 얼마나 흡수했는가"를 재는 것인데, **실험 도중
잔액이 떨어지면 그게 전부 레이트 리밋으로 집계된다.** 결제 사고를 보고
"우리 리미터가 부족하다"는 결론을 내리게 된다.

같은 429여도 뜻이 완전히 다르다.

| 코드 | 뜻 | 재시도 |
|---|---|---|
| `rate_limit_exceeded` | 지금 말고 나중에 | 한다 |
| `insufficient_quota` | 결제하기 전까지 영원히 안 됨 | **안 한다** |

### 어떻게 막았나

상태 코드만 보지 않고 **본문의 오류 코드까지 본다.**

```python
_TERMINAL_ERROR_CODES = frozenset({"insufficient_quota", "billing_hard_limit_reached"})

def is_quota_exhausted(exc): return getattr(exc, "code", None) in _TERMINAL_ERROR_CODES
```

계측도 `rate_limited`와 `quota_exhausted`로 갈라 센다.

### 배운 것

**HTTP 상태 코드는 분류의 시작이지 끝이 아니다.** 429 하나에 성격이 다른
상황이 여럿 들어간다. 재시도 여부처럼 중요한 판단을 상태 코드만으로 내리면
"다시 걸면 되는 것"과 "다시 걸면 안 되는 것"이 한 덩어리가 된다.

그리고 **이건 실제로 호출해봐야만 나온다.** 목으로 짠 429는 우리가 정한
모양대로만 오기 때문에, 제공사가 같은 코드에 다른 의미를 실어 보낸다는 것을
알 수 없다.

### 재발 방지

`test_quota_exhaustion_is_not_retried`, `test_quota_exhaustion_counts_separately`.
목으로 쓰는 응답 본문은 **실제로 받은 것을 그대로 옮겨 적었다.**

## 🟡 `incorrect`는 `correct`를 포함한다 (Phase 3)

LLM 판정 응답을 불리언으로 바꾸는 자리다. 이렇게 짜면 **모든 오답이 정답이 된다.**

```python
if "correct" in text:   # "incorrect"도 통과한다
    return True
```

`startswith`로 바꿔도 순서가 틀리면 같은 결과다. `correct`를 먼저 검사하면
`"incorrect"`가 `"correct"`로 시작하지 않으므로 괜찮지만, 헷갈리기 쉬워서
**부정형을 먼저 보는 순서로 고정**하고 테스트로 못박았다.

해석할 수 없는 응답은 **추측하지 않고 예외를 던진다.** 임의로 오답 처리하면
틀린 판정이 조용히 평가 데이터에 남고, 나중에 임계값을 그 오염된 데이터로 정하게 된다.

> 이 자리가 무서운 이유는 **틀려도 아무것도 안 터진다는 것**이다. 판정이 조용히
> 뒤집히고 정확도만 이상해진다. 원인을 찾기 매우 어렵다.

## 🟡 코사인 "거리"와 "유사도"는 반대다 (Phase 3)

Chroma가 돌려주는 것은 **거리**다. 코사인 공간에서 `거리 = 1 - 유사도`.
그대로 쓰면 정답이 0점이 되고 오답이 만점이 된다.

**이건 목으로는 절대 안 잡힌다.** 벡터 스토어를 목으로 두면 우리가 넣은 값이
그대로 나오므로 단위 테스트는 전부 통과하면서 실제 판정만 반대로 나온다.

그래서 Chroma를 **실제로 띄워서** 테스트했다. 손으로 만든 직교 벡터를 넣고
유사도가 1.0과 0.0으로 나오는지 확인한다.

```python
Q1_VECTOR = [1.0, 0.0, 0.0]
Q2_VECTOR = [0.0, 1.0, 0.0]   # 직교 → 유사도 0
```

### 배운 것

**목으로 대체할 수 있는 것과 없는 것을 나눠야 한다.** 목의 목적은 외부 의존을
끊는 것이지 "우리가 그 의존을 올바르게 쓰고 있는가"를 검증하는 게 아니다.
값의 의미를 변환하는 경계(거리↔유사도, 초↔밀리초, 0-based↔1-based)는
**실물로 한 번은 확인해야 한다.**

## 🟡 계측 카운터가 서로 다른 실패를 한 칸에 담았다 (Phase 3.5)

부하 스크립트를 처음 돌렸을 때 이렇게 나왔다.

```
llm.giveup: 12
```

"429를 다 맞고 12번 포기했다"로 읽힌다. **실제로는 API 키가 없어서 즉시 실패한
것**이었다. 재시도는 한 번도 안 했다.

측정값이 거짓말을 하고 있었다. 부하 실험의 목적이 "대응이 얼마나 흡수했는가"를
재는 것인데, 그 숫자에 관계없는 실패가 섞이면 표를 채워도 의미가 없다.

```python
if is_retryable(exc):
    metrics.increment(f"{operation}.giveup")   # 다시 걸어봤는데도 안 됨
else:
    metrics.increment(f"{operation}.failed")   # 애초에 다시 걸 대상이 아님
```

### 배운 것

**계측은 코드를 짤 때가 아니라 출력을 읽을 때 검증된다.** 카운터 이름이
그럴듯해도 실제로 무엇이 그 칸에 들어가는지는 한 번 돌려봐야 안다.
숫자를 근거로 쓸 계획이라면 **그 숫자가 무엇을 세는지부터 실물로 확인**해야 한다.

## 🔵 판정 근거를 남길 컬럼이 없었다 (Phase 3)

개발 계획에는 "판정 레코드에 임베딩 모델 ID와 템플릿 버전을 함께 남긴다"가
적혀 있는데 **DB 스키마에 그 컬럼이 없었다.** 계획 문서와 스키마 문서가 따로
작성되면서 어긋난 것이다.

### 배운 것

문서가 여러 개면 **문서끼리도 어긋난다.** 구현 직전에 관련 문서를 다 읽고
대조하는 단계가 필요하고, 어긋난 것을 찾으면 **문서를 먼저 고치고 구현한다.**
코드를 먼저 맞추면 문서가 거짓말이 된 채로 남는다.

## ⚪ 측정을 시작하기 전에 측정을 오염시킬 것부터 막았다 (Phase 3.5 이후)

### 배경

임계값 `0.82 / 0.55 / margin 0.05`은 근거 없이 정한 값이라 실제 유사도 분포를
재서 확정해야 한다. 그 측정을 시작하기 직전에 코드를 훑었더니, **측정 결과를
조용히 망가뜨릴 수 있는데 아무 신호도 남기지 않는 경로**가 셋 있었다.

측정 도구를 만들기 전에 이것부터 막았다. 순서를 바꾸면 나중에 "그때 그 숫자가
맞는 숫자였나"를 되짚을 수 없게 된다.

### 1. 임베딩 응답 순서를 그대로 믿고 있었다

```python
return [item.embedding for item in response.data]     # 전
items = sorted(response.data, key=lambda item: item.index)   # 후
```

배치로 60건을 한 번에 임베딩하는데 응답 배열 순서를 입력 순서와 같다고 보고
`zip`으로 붙이고 있었다. **응답 항목에 `index` 필드가 있다는 것 자체가 배열
순서를 보장하지 않는다는 뜻이다.**

순서가 어긋나면 앵커에 남의 벡터가 저장된다. 개수는 맞으니 `zip(strict=True)`도
통과하고 예외도 안 난다. **유사도만 전부 엉터리가 되는데 그게 임계값이 잘못
잡힌 것인지 벡터가 뒤바뀐 것인지 구분할 방법이 없다.**

### 2. 앵커 적재 실패가 종료 코드 0으로 끝났다

```python
except ExternalServiceError as exc:
    print(f"앵커 적재 실패: {exc}")
    return                      # ← 종료 코드 0
```

"DB는 채워졌는데 앵커는 없는" 상태가 성공처럼 보였다. 그 상태로 서버를 띄우면
`judge_service`가 `similarity is None`을 보고 **모든 답변을 LLM 폴백으로 보낸다.**
비용은 오르고 하이브리드는 꺼져 있는데 어디에도 실패 신호가 없다.

### 3. 적재했다는 말을 스토어에 확인하지 않았다

`replace_anchors`를 부르고 나서 실제로 몇 건이 들어갔는지 묻지 않았다.
`vector_store.count()`를 추가해 넣으려 한 수와 대조하고, 기대 정답이 비어 있는
문항이 있으면 아예 시작하지 않게 했다.

### 배운 것

**조용한 실패는 "예외가 안 나는 실패"가 아니라 "측정값이 오염되는 실패"다.**
서비스가 멈추는 고장은 금방 알지만, 판정 품질만 떨어지는 고장은 그걸 재려고
만든 측정 자체가 오염되어 있어서 영원히 모른다.

그래서 순서가 중요하다. **측정 도구를 만들기 전에 측정 대상의 무결성을 먼저
보장한다.** 반대로 하면 나중에 나온 숫자를 믿을 근거가 없다.

### 재발 방지

테스트 8건 추가 (`tests/test_embedding_client.py`, `tests/test_seed_integrity.py`).
특히 **응답을 일부러 뒤섞어 넣고 입력 순서대로 나오는지** 보는 테스트가 핵심이다.
이건 실제 API로는 재현할 수 없고 목으로만 고정할 수 있다.

### 남은 것

같은 감사에서 나온 것 중 **일부러 안 고친 것**이 있다. 부정문 오답이 상한과
margin을 둘 다 통과할 수 있다는 지적인데, 지금 고치면 **정말 통과하는지 확인할
기회를 잃는다.** 평가 데이터셋에 부정문을 넣어 실측한 뒤에 대응한다.

> 원칙: **측정을 오염시키는 것만 먼저 고치고, 측정이 답을 줄 것은 남긴다.**

## 🟡 측정 도구의 "추천"이 가치 판단을 숨기고 있었다 (임계값 확정 준비)

### 무슨 일이 있었나

임계값 스윕 스크립트를 만들고 합성 데이터로 돌려봤다. 추천이 이렇게 나왔다.

```
추천: upper=0.94, lower=0.7   FA 0건, FR 12건, LLM 위임 50.0%
```

그런데 표 바로 아래 줄에 이런 조합이 있었다.

```
0.94   0.62   61.6%    0    0  100.0%
```

**오답을 정답으로 확정하는 오류(FA)는 양쪽 다 0인데, 추천이 고른 쪽은 정답을
오답으로 확정하는 오류(FR)를 12건 내고 있었다.** 그걸 LLM 위임 11.6%p와 맞바꾼 것이다.

### 왜 그랬나

정렬 키를 이렇게 썼다.

```python
best = min(clean, key=lambda g: (g["llm"], g["fr"]))   # 비용이 1순위
```

의도는 "false accept가 없는 것 중 가장 싼 것"이었는데, **false reject를 비용
뒤에 두면서 "오류를 돈으로 산다"는 판단이 코드에 박혔다.** 판정 시스템에서
그 교환은 성립하지 않는다. 사용자는 자기 정답이 오답 처리된 것을 겪고,
우리는 그걸 절약이라고 부른 셈이다.

### 어떻게 고쳤나

확정 오류가 0인 지점이 있으면 **그중에서** 가장 싼 것을 고르고, 없을 때만
오류 최소로 내려간다. 그리고 **버린 선택지를 같이 출력한다.**

```
추천: upper=0.94, lower=0.62   (확정 오류 0건 중 가장 싼 조합)
참고: 가장 싼 것은 upper=0.94, lower=0.7 (LLM 50.0%)인데 FR 12건을 낸다.
      오류 12건을 없애는 값이 LLM 위임 11.6%p다. 이 교환을 받을지는 사람이 정한다
```

### 배운 것

**측정 도구는 중립이 아니다.** 숫자를 보여주는 것까지는 중립이지만 "추천"을
찍는 순간 무엇이 더 중요한지에 대한 판단이 들어간다. 그 판단이 정렬 키 한 줄에
숨어 있으면 읽는 사람은 그게 판단인 줄도 모르고 받아들인다.

그래서 두 가지를 원칙으로 잡았다.

- **추천에는 근거 문구를 붙인다.** "확정 오류 0건 중 가장 싼 조합"처럼 무엇을
  먼저 봤는지 한 줄로 밝힌다
- **버린 선택지를 같이 보여준다.** 교환 조건을 수치로 제시하고 결정은 사람에게 남긴다

### 재발 방지

합성 데이터로 스윕을 돌려보는 것 자체가 이 검사였다. **실제 데이터가 없어도
도구의 판단 로직은 검증할 수 있다.** 오히려 분포를 내가 정하니까 "이 상황에서
이런 추천이 나와야 한다"를 미리 알고 확인할 수 있었다.

## 🔵 margin 조건은 지금 시드 구성으로는 발화하지 못할 수 있다 (평가셋 2차)

### 무엇을 발견했나

평가셋 2차에서 margin 프로브 40건을 일부러 만들었다. 그런데 커버리지 점검이
**그 40건이 이름과 달리 margin을 건드리지 못한다**고 지적했다.

발화 조건을 다시 보면 이렇다.

```python
sim >= upper  AND  (sim - rival) < margin      # 이때만 LLM으로 넘어간다
```

`rival`은 **다른 문항** 앵커 중 최고 유사도다. 즉 발화하려면 한 답변이
**자기 문항 앵커와 남의 문항 앵커 양쪽에 동시에 가까워야** 한다.

그런데 만든 40건은 둘 다 rival을 못 올린다.

| 카테고리 | 왜 안 되나 |
|---|---|
| margin-질문되뱉기 | "대한민국의 수도요"는 **자기 문항** 문구를 되뱉는다. 자기 앵커와만 가깝다 |
| margin-틀모방 | "대한민국의 수도는 부산입니다"는 sim만 높고 rival은 그대로 낮다 |

**둘 다 margin 프로브가 아니라 false accept 프로브였다.** 이름을 잘못 붙였다.

### 더 근본적인 문제

지금 20문항의 앵커가 **서로 의미적으로 떨어져 있다.** 수도, 행성, 왕, 대양,
올림픽 주기... 한 답변이 두 문항 앵커에 동시에 가까워지기 어려운 구성이다.
가장 가까운 축이라야 `섭씨 0도` vs `약 36.5도`(온도), `4년마다` vs `약 365일`(기간)
정도인데 이 정도로 rival이 상한 근처까지 오를지는 의문이다.

**즉 이건 데이터를 더 넣어서 푸는 문제가 아니라 시드 문항 구성의 문제다.**

그리고 `_is_confident_correct`의 주석이 주장하는 정당화 — "몰라요", "네" 같은
짧고 흔한 답변이 상한을 통과하므로 margin이 필요하다 — 도 **아직 검증된 적 없는
가설이다.** 그런 답변은 어느 앵커와도 표층이 안 겹쳐 애초에 상한을 못 넘길
가능성이 높고, 그러면 하한에서 끊겨 margin이 호출되지도 않는다.

### 그런데 지금 고치지 않는다

**측정이 답을 줄 문제이기 때문이다.** 위 논증은 임베딩이 어떻게 동작할지에 대한
추론이고, 그 추론을 근거로 설계를 바꾸면 우리가 방금까지 하지 않기로 한 일
(재보지 않고 판단하기)을 그대로 하는 것이 된다.

1차 회피성 12건이 이미 저 가설의 반증 표본으로 데이터셋에 들어 있다.
`scripts/analyze.py`의 2번 절이 "margin이 한 번도 발화하지 않았다"를 명시적으로
경고하도록 짜여 있으니, 측정을 돌리면 바로 드러난다.

### 측정 결과에 따른 분기

| 결과 | 대응 |
|---|---|
| margin이 발화하고 오통과를 막는다 | 유지. 정당화가 실측으로 확보된다 |
| 한 번도 발화 안 한다 | **장치를 걷어내거나**, 의미가 인접한 문항 쌍을 시드에 추가해 rival이 오르는 구성을 만든다 |
| 발화하는데 전부 정답을 막는다(헛수고) | margin 값을 낮추거나 조건 자체를 재설계 |

### 배운 것

**프로브를 만들 때 "무엇을 겨냥하는가"와 "그 지표가 실제로 무엇에 반응하는가"를
따로 확인해야 한다.** margin 프로브라고 이름 붙이고 40건을 만들었지만, 지표의
정의를 다시 읽어보니 그중 0건이 그 지표를 움직이지 못했다.
이름이 검증을 대신해주지 않는다.

## 🔴 정규화가 답변을 빈 문자열로 만들어 임베딩이 400을 냈다 (임계값 측정)

### 무슨 일이 있었나

평가셋 372건으로 첫 측정을 돌렸더니 임베딩 호출이 통째로 실패했다.

```
Error code: 400 - {'error': {'message': "Invalid 'input[13]': input cannot be an empty string."}}
```

`input[13]`은 `"."`이었다. `render(".")`가 끝 문장부호를 지우면서 **빈 문자열**이
됐고, 제공사가 빈 입력을 거부했다.

### 왜 문제인가

**측정 스크립트만의 문제가 아니라 실서비스 경로가 같다.**

```
"." -> AnswerRequest 검증(min_length=1) 통과 -> render() -> "" -> embed_one("") -> 400
```

400이 `ExternalServiceError`로 포장되면 `judge_service`의 `except`에 잡혀 LLM
폴백으로 간다. 판정 자체는 되지만 **원인이 외부 장애로 기록된다.** 제공사는
멀쩡한데 우리가 보내면 안 되는 입력을 보낸 것이고, 실패율 지표가 그만큼 오염된다.
절대 성공할 수 없는 호출에 쿼터도 쓴다.

### 어떻게 고쳤나

`judge_service.judge`에서 임베딩을 부르기 **전에** 걷어낸다.

```python
if not normalization.render(answer_text):
    return await _judge_by_llm(question, answer_text, JudgeMethod.FALLBACK)
```

결과 경로는 같은 폴백이지만 **원인이 정확해진다.** 외부 실패로 세지 않고
호출도 나가지 않는다.

### 배운 것

**입력 검증은 정규화 전 값이 아니라 정규화 후 값에 걸어야 한다.**
`min_length=1`은 원문을 보는데 실제로 외부에 나가는 것은 `render()`를 거친
문자열이다. 둘 사이에 값이 바뀌는 변환이 끼어 있으면 검증이 그 변환 뒤로
따라가지 않는 한 구멍이 남는다.

그리고 이건 **평가 데이터셋이 잡아낸 첫 실제 버그다.** `정규화-빈문자열`
카테고리는 "임베딩 API가 빈 입력을 어떻게 처리하는지 실측 대상"이라는 메모와
함께 5건 만들어둔 것이었고, 첫 실행에서 바로 터졌다.
**케이스를 의도적으로 설계하면 그 케이스가 실제로 걸린다.**

## 🟡 부정어 규칙이 받침 때문에 절반을 놓쳤다 (D안)

부정 표현을 잡으려고 `아니|아냐`로 정규식을 짰다. 평가셋으로 재봤더니
**상한 통과 부정문 14건 중 6건을 놓쳤다.**

놓친 것들을 보고 원인을 알았다.

```
"아닙니다" = 아 + 닙 + 니 + 다     <- 부분 문자열 "아니"가 없다
"아닌 것"  = 아 + 닌 + ...
```

어간 `아니-`에 어미가 붙으면 `니`에 받침이 들어가 **다른 음절**이 된다.
`아[니닙닌냐님녜]`로 활용형을 열거해 14건 전부 잡았다.

### 배운 것

**한글은 음절 단위로 조합되므로 형태소가 문자열에서 쪼개지지 않는다.**
`아니-`라는 어간은 활용하면 `아니`, `아닙`, `아닌`, `아냐`, `아님`으로 **음절 자체가 바뀐다.**
영어라면 `not`이 그대로 남지만 한글은 안 그렇다.

조사 선택(`이/가`, `은/는`, `을/를`)이 어려운 것도 같은 원인이다.
**한국어를 문자열 규칙으로 다루기로 했다면 받침을 반드시 따로 설계해야 한다.**

### 규칙을 데이터로 정했다는 것

이 오류를 잡을 수 있었던 건 **규칙을 짜자마자 평가셋으로 재봤기 때문이다.**
후보 규칙 네 개를 만들어 "상한 통과 부정문 중 몇 건을 잡는가"와
"정답에 몇 건 오작동하는가"를 표로 비교했다. 눈으로 봤으면 `아닙니다`가
`아니`를 포함하지 않는다는 것을 알아채지 못했을 것이다.

## 🔵 아무 일도 안 하는 안전장치가 있었다 (C안)

### 발견

정답 확정에 조건이 둘이었다. 상한 통과, 그리고 다른 문항 앵커와의 차이(margin).
두 번째 조건이 **평가셋 372건에서 한 번도 발화하지 않았다.** 세 단계 내내 0건.

지우고 다시 재봤더니 **FA 11, FR 27, LLM 위임 32.7%로 전후가 완전히 동일했다.**

### 왜 이런 게 생겼나

조건을 넣을 때 근거가 있었다. 주석에 이렇게 적혀 있었다.

> "몰라요", "네" 같은 짧고 흔한 답변이 상한을 통과한다. 그런 답변은
> 모든 문항에 두루 가까우므로 두 유사도의 차이를 보면 걸러진다.

**그럴듯한데 재본 적이 없었다.** 실제로 재보니 회피성 답변의 유사도 중앙값은
0.256이었다. 상한 0.82 근처에도 안 온다. 막아야 할 대상이 그 근처에 오지도 않는데
막는 장치를 만들어둔 것이다.

### 배운 것

**"그럴듯한 근거"와 "측정된 근거"는 다르다.**

이 조건은 논리가 틀리지 않았다. 짧고 흔한 답변이 여러 문항에 두루 가까울 것이라는
추론 자체는 합리적이다. **다만 그런 답변이 애초에 상한을 못 넘는다는 사실을
확인하지 않았다.** 전제의 앞단이 비어 있었다.

그리고 이런 코드는 **있는 것이 없는 것보다 나쁘다.** 읽는 사람이 "여기 방어가
있다"고 믿게 만들고, 그 믿음은 재보기 전까지 깨지지 않는다.

### 지웠지만 관측은 남겼다

`rival_similarity`는 계속 재서 기록한다. `analyze.py`의 `rival_watch`가
"상한 통과분 중 rival이 0.05 이내로 붙은 것"을 매번 센다. 지금은 0건이고,
문항이 늘어 주제가 겹치면 올라간다. **되살릴 조건을 수치로 정의해둔 것이다.**

지운 것보다 이쪽이 실제 산출물에 가깝다.

## 🟡 코드 기본값을 바꿨는데 `.env`가 덮어쓰고 있었다 (임계값 확정)

측정으로 정한 임계값을 `config.py`에 반영하고 분석을 다시 돌렸는데 **출력이 그대로
`upper=0.82, lower=0.55`였다.** 코드를 세 번 확인해도 `0.90 / 0.26`이 맞았다.

`.env`에 옛 값이 박혀 있었다.

```
UPPER_THRESHOLD=0.82      <- 이게 이긴다
LOWER_THRESHOLD=0.55
MIN_MARGIN=0.05           <- 코드에서 제거한 설정인데 남아 있었다
```

pydantic-settings는 환경변수와 `.env`를 코드 기본값보다 **우선**한다. 당연한
동작인데, "설정을 바꿨다"고 생각할 때 고치는 곳은 보통 코드 쪽이라 놓친다.

### 왜 위험한가

**아무 에러도 안 난다.** 옛 값으로 조용히 돈다. 게다가 `extra="ignore"` 때문에
이미 제거한 `MIN_MARGIN`이 남아 있어도 경고 한 줄 없다.

그리고 이건 **사람마다 다르게 도는** 종류의 문제다. 리포를 새로 받은 사람은
코드 기본값(0.90)으로 돌고, `.env`를 오래 들고 있던 사람은 0.82로 돈다.
같은 코드인데 판정 결과가 다르다.

### 어떻게 막았나

`.env`와 `.env.example` 양쪽을 고치고 제거된 키를 지웠다. 근본적으로는
**설정의 단일 원본을 정하고 나머지는 그 사본임을 문서에 명시**해야 한다.

### 배운 것

**"설정을 바꿨다"는 코드를 고쳤다는 뜻이 아니다.** 값이 어디서 오는지 경로가
여럿이면 우선순위를 알고 있어야 하고, 바꿀 때는 **실제로 로드된 값을 찍어서
확인**해야 한다. 이번에도 분석 출력의 헤더에 임계값이 찍히지 않았으면
잘못된 값으로 결론을 냈을 것이다.

> 분석 스크립트가 매번 `(upper=..., lower=...)`를 출력하도록 해둔 것이 이걸 잡았다.
> **측정 도구는 자기가 무슨 설정으로 돌았는지 항상 같이 찍어야 한다.**

## 🔴 게이트를 켰더니 DB 커넥션 풀이 터졌다 (Phase 3.5 실측)

### 무슨 일이 있었나

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 20 overflow 40 reached,

```

### 왜 그랬나

**요청이 게이트 대기줄에 서 있는 내내 DB 커넥션을 쥐고 있다.**

```
요청 도착 -> DB 세션 열림 -> 세션 조회 -> 게이트 대기(최대 수십 초) -> LLM 호출 -> 저장 -> 세션 닫힘
             ^^^^^^^^^^^^                 ^^^^^^^^^^^^^^^^^^^^
             여기서 커넥션을 잡고          이 내내 놓지 않는다
```

게이트가 흐름을 조일수록 대기가 길어지고, 길어진 만큼 커넥션이 오래 묶인다.
동시 120건이 들어오는데 풀이 60이면 60건이 대기하고, 30초 안에 자리가 안 나면
타임아웃이다.

**즉 429를 막았더니 커넥션 풀이 새 병목이 됐다.** 두 대응이 서로 간섭한다.

### 배운 것

**한 층의 병목을 없애면 다음 층이 드러난다.** 그리고 그 다음 층은 처음에는
안 보인다. 부하가 낮을 때는 대기가 짧아서 커넥션 점유 시간도 짧기 때문이다.
**흐름 제어를 넣기 전에는 존재하지 않던 문제**를 흐름 제어가 만들어냈다.

더 일반화하면 **"자원을 쥔 채로 기다리지 마라"**다. 외부 호출처럼 오래 걸리는
작업 앞에서는 잡고 있는 자원을 놓아야 한다. 게이트는 이미 그렇게 짜여 있었다
(`test_gate_is_free_while_backing_off` — 백오프 중에는 세마포어를 놓는다).
**같은 원칙을 DB 커넥션에는 적용하지 않았다.**

### 아직 안 고쳤다

근본 해법은 외부 호출 전에 커넥션을 놓는 것인데 트랜잭션 경계를 다시 설계해야 한다.
지금은 **풀 크기를 설정으로 빼서 병목 위치를 드러내는 데까지** 했다.
`docs/notes/concurrency.md`에 남은 과제로 적어뒀다.

### 곁가지로 확인한 것

풀을 15에서 60으로 늘려 재보니 **처리량은 11.1 -> 11.5/s로 그대로인데 지연만
8.19초 -> 1.97초로 4배 좋아졌다.** 풀은 처리량이 아니라 지연의 병목이었다.
처리량 천장은 제공사 응답 속도다.

**동시성을 25에서 120으로 5배 올려도 처리량이 8.8에서 11.1로만 오른 것**이
포화의 신호였는데, 그때는 풀 때문인 줄 알았다. 재보고 나서야 갈렸다.

## 🟡 재시도만 켜면 부하가 3배가 되고 성공률은 그대로다 (Phase 3.5 실측)

같은 부하에서 재시도만 켰더니 이렇게 나왔다.

| | 대응 없음 | 재시도만 |
|---|---|---|
| 성공률 | 39.8% | 42.6% |
| LLM 호출 시도 | 1,200 | **3,326** |
| 429 발생 | 722 | **2,814** |
| **성공 1건당 호출** | 2.5 | **6.5** |

**성공률은 2.8%p 오르고 호출은 2.8배가 됐다.** 재시도가 근본 원인(과다 유입)을
건드리지 않고 같은 한도에 더 많이 부딪히게 만들었다. 429가 재시도를 부르고
그 재시도가 다시 429를 만드는 **재시도 폭풍**이다.

### 배운 것

**재시도는 흐름 정형의 대체재가 아니라 보완재다.** 흐름을 안 조인 채 재시도만
켜면 비용은 몇 배가 되고 성공률은 거의 그대로다. 반대로 게이트를 켠 뒤에는
재시도를 추가해도 +0.4%p뿐이었다. **429가 0이라 재시도할 것이 없기 때문이다.**

그래도 재시도를 남기는 이유는 게이트가 못 막는 경우를 위한 안전망이라서다.
다른 클라이언트가 같은 쿼터를 쓰거나 제공사가 일시적으로 한도를 낮추면
우리 게이트 설정과 무관하게 429가 온다.

## 🔴 페르소나를 붙였더니 테스트가 실제 API를 부르기 시작했다 (Phase 4)

### 무슨 일이 있었나

페르소나 레이어를 세션 흐름에 연결하고 테스트를 돌렸더니 **전체 실행이
0.8초에서 62초로 늘었다.** 두 건이 실패했는데 실패 메시지가 이랬다.

```
assert '안녕! 퀴즈에 참가해 줘서 고마워. 이제 시작해 볼게! 준비됐지?' is None
```

`None`이어야 할 자리에 **실제 모델이 생성한 문장**이 들어 있었다.
테스트가 진짜 OpenAI를 부르고 있었던 것이다.

### 왜 그랬나

지금까지 LLM을 부르는 곳은 판정 하나뿐이었고, 그건 각 테스트가 필요할 때
목으로 갈아끼우고 있었다. 그런데 페르소나를 붙이면서 **호출 지점이 넷으로 늘었다.**

```
세션 시작 -> 오프닝 멘트
문제 출제 -> 출제 멘트
답변 제출 -> 리액션 멘트
세션 종료 -> 마무리 멘트
```

목을 깜빡한 테스트가 **그 자리에서 조용히 실제 호출을 한다.** 실패한 두 건은
`host_message is None`을 단정하고 있어서 드러났지만, **그 단정이 없는 테스트는
호출하고도 통과한다.** 통과하니까 아무도 모른다.

### 어떻게 막았나

`conftest.py`에 **autouse 목**을 넣었다.

```python
@pytest.fixture(autouse=True)
def block_host_message(monkeypatch):
    async def fake(system_prompt, user_message):
        return "[목 진행 멘트]"
    monkeypatch.setattr(llm, "generate_host_message", fake)
```

**autouse인 것이 핵심이다.** 개별 테스트가 목을 거는 방식이면 새 테스트를
쓸 때마다 잊을 수 있다. 기본값이 "아무것도 안 나간다"여야 하고, 실제 호출을
보고 싶은 테스트가 있으면 그쪽에서 덮어쓰게 한다.

### 배운 것

**외부 호출 지점이 늘어나면 목 전략도 같이 바뀌어야 한다.** 호출이 한 곳일
때는 개별 목으로 충분했지만 넷이 되자 "빠뜨릴 수 있는 구조"가 됐다.

그리고 이런 사고는 **비용과 속도로 먼저 드러난다.** 실행 시간이 78배가 된 것이
신호였고, 만약 호출이 한두 번이었으면 눈치채지 못한 채 CI에서 계속 돈이
나갔을 것이다. **테스트 실행 시간이 갑자기 늘면 원인을 확인해야 한다.**

> 판정 프롬프트를 처음 붙일 때 같은 실수를 안 한 이유는 그때 호출 지점이
> 하나였기 때문이다. **잘해서가 아니라 구조가 단순해서 안 틀린 것**이고,
> 구조가 복잡해지자 바로 틀렸다.

## 🔴 문턱을 넘겼다고 믿고 세부를 비교하고 있었다 (Phase 4)

### 무슨 일이 있었나

프롬프트 캐싱 실험을 세 번 돌렸는데 매번 결론이 안 나왔다. 배치를 바꿔가며
"프리픽스를 앞에 두는 것이 나은가"를 재고 있었는데 수치가 뒤죽박죽이었다.

원인은 **캐싱이 애초에 안 걸리고 있었다**는 것이다.

### 왜 몰랐나

프리픽스를 만들고 토큰을 재니 **1,032**가 나왔다. 최소 요건이 1,024라고
측정해뒀으니 **"8토큰 차이로 넘겼다"**고 판단하고 넘어갔다.

실제로는 **120토큰이 부족했다.**

```
적중량 = (floor(공통 토큰 / 128) - 1) x 128

1,032토큰 -> floor(1032/128) = 8블록 -> (8-1) x 128 = 896 < 1,024   안 걸림
1,152토큰 -> floor(1152/128) = 9블록 -> (9-1) x 128 = 1,024         걸림
```

**갈라지는 지점이 들어 있는 마지막 블록은 캐시되지 않는다.** 그래서 실질
문턱은 1,024가 아니라 9블록, 즉 1,152토큰이다. 이걸 몰랐다.

### 어떻게 찾았나

같은 프리픽스를 가진 두 프롬프트를 길이만 바꿔가며 불러 적중을 표로 만들었다.
8블록에서 0, 9블록부터 1,024가 나오는 것을 보고 규칙을 역산했다.

### 배운 것

**"A와 B 중 뭐가 나은가"를 묻기 전에 "그게 작동은 하는가"를 확인해야 한다.**

이 프로젝트에서 여러 번 쓴 원칙인데(임계값을 정하기 전에 분포를 봤고, 대응을
비교하기 전에 429를 재현했다) **여기서는 건너뛰었다.** 이유는 단순하다.
숫자가 1,032이고 문턱이 1,024라서 **계산해볼 필요를 못 느꼈다.**

**여유가 작을수록 계산해야 한다.** 8토큰 차이는 "넘었다"가 아니라
"확인해야 한다"는 신호였다.

### 부수 효과 — 결론이 하나 뒤집혔다

앞서 "캐싱을 걸려고 프롬프트를 늘리면 2.2배 손해"라고 계산해뒀는데,
그건 273토큰에서 출발할 때 이야기였다. **1,032에서 1,152로 120토큰만 늘리면
비용이 35% 줄어든다.** 같은 원리인데 출발점이 어디냐로 부호가 바뀐다.

문서에 단정으로 적어둔 것을 조건부로 정정했다.

## 🟡 지표가 0을 보고했는데 실제로는 8이었다 (Phase 4)

### 무슨 일이 있었나

페르소나 설정이 실제로 출력을 가르는지 보려고 말투 지표를 만들었다.
반말 어미를 세는 정규식을 넣고 돌렸더니 **두 페르소나 다 0회**가 나왔다.

```
불꽃     느낌표  12회  존댓말 어미   0회  반말 신호   0회
고요     느낌표   0회  존댓말 어미  10회  반말 신호   0회
```

느낌표와 존댓말은 완벽하게 갈렸는데 반말만 양쪽 0이었다. 그런데 불꽃의 실제
출력은 `"정답이야! 잘했어! 다음 문제로 가자!"`다. **명백히 반말인데 0회다.**

### 왜 그랬나

정규식이 이랬다.

```python
r"(야|어|지|자|해|줘|볼게|거든)\s|[야어지자해]$"
```

두 갈래 다 안 맞았다.

- `\s`(공백)를 요구했는데 실제 문장은 `"잘했어!"`처럼 **문장부호로 끝난다**
- `$`는 **문자열 전체의 끝**이라 문장이 여러 개면 마지막 하나만 본다

더 근본적으로는 **위치를 조건에 안 넣은 것**이 문제다. 한국어에서 `어`, `자`, `야`는
**문장 끝에서만 어미**이고 중간에서는 다른 형태소다.

```
"있어"의 어  -> 어미      "어디"의 어  -> 어미 아님
"가자"의 자  -> 어미      "자세히"의 자 -> 어미 아님
```

### 어떻게 고쳤나

문장 끝 위치를 전방 탐색으로 조건에 넣었다.

```python
r"[어아야지자해네](?=[!?.]|$)"
```

실제 출력으로 다시 재니 **불꽃 8회, 고요 0회.** 눈으로 본 것과 맞는다.

### 배운 것

**지표가 "없다"고 말할 때 그게 진짜 없는 것인지 못 잡은 것인지 구분해야 한다.**

이번에는 다른 지표(느낌표, 존댓말)가 정상 작동해서 대조가 됐고, 실제 출력을
눈으로 보고 있었기 때문에 이상하다는 것을 알아챘다. **지표 하나만 봤으면
"설정이 말투를 안 가른다"는 정반대 결론을 냈을 것이다.**

> **0은 가장 의심스러운 값이다.** 다른 값은 틀려도 "이상한데" 싶은데
> 0은 "없나 보다"로 넘어가기 쉽다.

### 한국어 문자열 처리로 틀린 것이 이번이 두 번째다

| | 무엇 | 원인 |
|---|---|---|
| D안 | 부정어 규칙 `아니\|아냐`가 `"아닙니다"`를 못 잡음 | **받침**이 붙어 음절이 바뀜 |
| 이번 | 반말 어미 정규식이 0회를 보고 | **위치**를 조건에 안 넣음 |

**둘 다 "형태소를 문자열로 다룰 때"의 함정이다.** 영어라면 `not`이 그대로
남고 공백으로 단어가 갈리는데, 한국어는 **음절이 조합되고 어미가 붙는다.**

정리하면 한국어를 정규식으로 다룰 때 최소한 이 둘은 매번 확인해야 한다.

1. **받침이 붙으면 음절이 바뀌는가** (`아니` -> `아닙`, `아닌`)
2. **그 형태소가 어느 위치에서만 유효한가** (어미는 문장 끝에서만)
