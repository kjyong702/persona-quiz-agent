# 중복 제출과 DB 안전망

> 재현: `uv run pytest tests/test_duplicate_submit.py`

## 창이 넓다

답변 제출은 `check-then-act` 구조다.

```
1. 세션과 현재 문항을 읽는다
2. 판정한다                       <- **여기서 수 초 걸린다 (LLM 호출)**
3. 답변을 저장한다
```

**2번이 창이다.** 같은 답변이 동시에 두 번 들어오면 둘 다 1번을 통과하고
둘 다 판정을 받고 둘 다 저장된다. 사용자가 버튼을 두 번 누르거나 네트워크가
끊겨 재전송하면 실제로 일어난다.

일반적인 웹 요청이면 창이 밀리초라 확률이 낮은데, **LLM 호출이 끼면 초 단위가 된다.**

## 왜 멱등 키를 안 두었나

중복 요청을 막는 정석은 **멱등 키(idempotency key)**다. 클라이언트가 요청마다
고유한 키를 만들어 보내고 서버가 그 키로 중복을 가른다. 결제 API가 이 방식이다.

**여기서는 안 썼다. 자연 키가 이미 있기 때문이다.**

```sql
CONSTRAINT uq_session_question UNIQUE (session_id, question_id)
```

**두 컬럼을 묶은 복합 유니크다.** 각각은 중복돼도 된다. 한 세션이 문항 10개를
품으므로 `session_id`는 반복되고, 한 문항을 여러 세션이 풀으므로 `question_id`도
반복된다. **금지되는 것은 그 조합이 두 번 나오는 것뿐이다.**

퀴즈 한 문항에는 답변이 하나뿐이라 이 조합이 유일하다. **멱등 키는 자연 키가
없을 때 만드는 것이다.** 결제는 같은 사람이 같은 금액을 두 번 보내는 것이
정당할 수 있어서 요청을 구분할 방법이 따로 필요하지만, 여기는 아니다.

> ⚠️ **되묻기(dev-plan Phase 9)를 넣으면 전제가 깨진다.** 한 문항에 답변이 여러 번
> 오게 되므로 제약에 시도 번호를 넣어야 한다.

## 걸렸을 때 어떻게 하나 — 409가 아니라 기존 결과

제약에 걸리면 `IntegrityError`가 난다. 그걸 잡아 **이미 저장된 답변을 돌려준다.**

**409로 거절하지 않는 이유**: 네트워크가 끊겨 다시 보낸 사용자에게 에러를 주는 것은
도움이 안 된다. 이미 채점됐고 그 결과는 바뀌지 않으므로 같은 답을 주는 쪽이 맞다.

이건 두 번째 요청의 판정이 **첫 번째와 다르게 나와도** 마찬가지다. LLM은
비결정적이라 같은 답변에 다른 판정이 나올 수 있는데, **먼저 저장된 것을 진실로
삼는다.** 사용자가 같은 답을 보내고 다른 점수를 받는 것이 더 나쁘다.

조회가 비어 있으면 다시 던진다. 제약이 걸렸는데 찾을 수 없다면 **다른 제약이
깨진 것**이므로 삼키면 안 된다.

## ⚠️ 제약은 마지막 방어선이지 첫 방어선이 아니다

**재봤다.** 판정에 0.3초가 걸린다고 가정하고 같은 답변을 동시에 5건 보냈다.

| | 저장된 행 | 판정 호출 |
|---|---|---|
| `UNIQUE (session_id, question_id)` 없음 | **5** | 5 |
| `UNIQUE (session_id, question_id)` 있음 | **1** | **5** |

흐름으로 보면 이렇다.

```
없을 때   요청1: 판정(0.3초) -> INSERT (1,1) -> 성공
         요청2: 판정(0.3초) -> INSERT (1,1) -> 성공     <- DB가 안 막는다
         ...  5행

있을 때   요청1: 판정(0.3초) -> INSERT (1,1) -> 성공
         요청2: 판정(0.3초) -> INSERT (1,1) -> **거부** (IntegrityError)
                                            -> 기존 행을 조회해 반환
         ...  1행
```

**핵심은 순서다.** `판정 -> INSERT` 순이라 **INSERT에서 막힐 때는 판정이 이미
끝나 있다.** 막으려면 `자리 선점 -> 판정 -> 채우기`로 순서를 바꿔야 한다.

**절반만 고쳐진다.** 데이터는 하나로 줄었는데 **LLM 호출은 그대로 5번이다.**
제약은 저장 시점에 걸리고, 그때는 이미 판정이 끝나 있다.

로그가 같이 작동하는 것도 확인했다.

```
[warning] answer.duplicate  session_id=1 question_id=1    x 4
```

**로깅이 없었으면 이 4번이 안 보인다.** 데이터는 깨끗하고 비용만 새는 상태라
증상이 없다.

실행 자체를 막으려면 **판정 전에 자리를 선점**해야 한다. 빈 행을 먼저 넣어
자리를 잡고, 판정한 뒤 그 행을 채우는 방식이다. 두 번째 요청은 선점 단계에서
막혀 LLM을 부르지 않는다.

**안 한 이유**: 판정이 실패하면 선점한 행을 정리해야 하고, 그 정리가 실패하면
그 문항이 영영 잠긴다. 지금 규모에서 중복 호출 비용보다 그 복잡도가 크다고 봤다.
**다만 트래픽이 늘면 이 판단은 뒤집힌다.**

## SQLite 외래키는 기본이 꺼져 있다

`ForeignKey`를 선언해도 SQLite는 **검사하지 않는다.** PRAGMA로 켜야 한다.

```python
@event.listens_for(engine.sync_engine, "connect")
def _enable_sqlite_foreign_keys(dbapi_connection, _record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.close()
```

**연결마다 걸어야 한다.** 커넥션 풀이 새 연결을 만들 때마다 초기화되므로
부팅 시 한 번 실행하는 것으로는 안 된다.

비동기 엔진에는 이벤트를 직접 못 걸어서 `sync_engine`을 쓴다. aiosqlite가 안에서
동기 드라이버를 돌리는 구조라 **실제 연결은 그쪽에서 만들어진다.**

**안 켜면 무슨 일이 생기나**: 없는 세션 ID로 답변을 넣어도 그냥 들어간다.
그리고 나중에 조회에서 빈 결과가 나올 뿐이라 **원인을 찾기 어렵다.**

## 검사에 이빨이 있는지 확인했다

테스트 5건이 통과했지만 **그것만으로는 확인이 안 된다.** 제약과 PRAGMA를 빼고
다시 돌렸다.

```
제약과 PRAGMA 제거 -> 5건 전부 실패
복원              -> 191건 전부 통과
```

동시 제출 테스트는 **세션을 다섯 개 만들어 실제로 경쟁시킨다.** 순차 호출만
확인하면 제약이 아니라 조회 로직을 테스트하는 셈이 된다.

### 테스트를 짜다 하나 배웠다 — `AsyncSession.get_bind()`

세션에서 엔진을 꺼내 새 세션을 만들려다 막혔다.

```
ArgumentError: AsyncEngine expected, got Engine(sqlite+aiosqlite:///...)
```

**`AsyncSession`은 안에 동기 `Session`을 감싸고 있고, `get_bind()`는 그 안쪽의
bind를 준다.** 독스트링에도 "synchronous proxied Session"이라고 적혀 있다.
즉 `AsyncEngine`이 아니라 `engine.sync_engine`이 나온다.

세션을 여러 개 만들어야 하므로 **엔진을 픽스처로 따로 냈다.**
`PRAGMA`를 `sync_engine`에 거는 것과 같은 이유의 구조다. **비동기 래퍼 아래에
동기 객체가 있고, 확장 지점은 대부분 그쪽에 있다.**
