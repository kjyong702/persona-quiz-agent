# 인덱스 드리프트 — 모델을 바꾸면 조용히 틀린다

> 재현: `uv run pytest tests/test_vector_store.py -k 드리프트`

## 무엇이 문제인가

저장된 앵커 벡터와 질의 벡터가 **다른 모델**이나 **다른 정규화 템플릿**에서 나오면
두 벡터는 서로 다른 공간에 있다. 그런데 코사인 유사도는 그냥 계산된다.

업계에서는 이 현상을 **index drift**라고 부른다. 임베딩 모델마다 고유한 기하 구조로
텍스트를 사상하므로, 모델을 바꾸면 좌표계가 바뀌고 **같은 텍스트라도 이전 모델의
벡터와는 비교할 수 없다.**

**가장 나쁜 종류의 실패다.** 500이 뜨면 알아채는데 이건 값이 나온다.
유사도가 조용히 망가지고 임계값 `0.92 / 0.24`가 의미를 잃는다.

## 차원이 막아주지 않는다

Chroma는 차원이 다르면 잡는다. 직접 확인했다.

```
Collection expecting embedding with dimension of 4, got 8
```

**그런데 차원이 같은 조합이 실재한다.**

| 모델 | 차원 |
|---|---|
| `text-embedding-ada-002` | 1536 |
| `text-embedding-3-small` (현재) | 1536 |
| `text-embedding-3-large` | 3072 (**1536으로 축소 가능**) |

**셋 다 1536으로 맞출 수 있다.** 갈아끼워도 예외가 안 난다.

## 필드는 이미 있었다. 아무도 안 읽었을 뿐이다

`scripts/seed.py`는 처음부터 레코드마다 `embedding_model`과 `template_version`을
넣고 있었다. 판정 결과 테이블과 API 응답에도 같은 두 필드가 있다.

**세 군데에 기록하면서 어디서도 대조하지 않았다.** 사고가 난 뒤 추적할 수는 있어도
사고를 막지는 못하는 상태였다.

`_replace_anchors_sync` 주석에는 이미 이렇게 적혀 있었다.

> 남아 있는 옛 벡터가 다른 모델이나 다른 템플릿으로 만들어진 것이면 비교가 성립하지 않는다

**위험을 알고 있었고 적재 쪽만 막았다.** 읽기 쪽은 비어 있었다.

## 정규화 템플릿이 더 위험하다

앵커도 `normalization.render()`를 타고 들어간다(`seed.py`). 그래서 인덱스는
**두 가지**에 묶여 있다.

```
인덱스 = f(임베딩 모델, 정규화 템플릿)
```

**템플릿 쪽이 더 자주 바뀐다.** 모델은 바꾸려면 마음먹고 바꾸지만 `normalization.py`는
규칙 한 줄 고치기가 쉽다. 실제로 `"."`이 빈 문자열이 되는 버그 때문에 손댈 뻔했다.

## 어떻게 막았나

**컬렉션 메타데이터에 도장을 찍고 읽을 때마다 대조한다.**

Chroma의 `get_or_create_collection`은 **컬렉션이 이미 있으면 넘긴 metadata를 무시하고
기존 것을 그대로 준다**(1.5.9에서 확인). 처음에는 제약처럼 보였는데 여기서는 오히려
유리하다. **도장이 인덱스를 만든 시점의 값으로 고정되고, 그것이 바로 알고 싶은 값이다.**

```
저장된 도장 != 지금 설정  ->  IndexDriftError  ->  503 INDEX_DRIFT
```

**폴백하지 않는다.** LLM으로 넘기면 편하지만 **인덱스가 깨진 것을 아무도 모르는 채
비용만 는다.** 판정이 안 되는 것보다 틀린 판정이 데이터에 쌓이는 쪽이 나쁘다.
LLM도 임베딩도 못 쓸 때 임의로 오답 처리하지 않는 것과 같은 판단이다.

도장이 아예 없으면 이 검사가 생기기 전에 만든 인덱스다. 판단할 근거가 없으므로
어긋났다고 보지 않는다. 다시 적재하면 도장이 찍힌다.

## 포괄 예외 처리가 방어를 두 번 지웠다

방어를 넣고 테스트를 짰더니 **잡히지 않았다.** 원인이 두 군데였다.

```
raise IndexDriftError(...)
  -> vector_store.match()의 except Exception
       -> VectorStoreUnavailableError로 다시 감쌈           <- 1차 소멸
  -> judge_service의 except ExternalServiceError
       -> "외부 장애니 LLM으로" 폴백                          <- 2차 소멸
```

`IndexDriftError`를 `ExternalServiceError` 계통에 둔 것이 원인이다. 계통을 나누면
호출자가 "외부 장애"로 뭉뚱그려 다루는데, **이건 재시도해도 낫지 않는 구성 오류다.**

두 곳 모두 포괄 처리보다 **먼저** 통과시키도록 고쳤다.

> **새 예외를 만들 때는 그것이 지나갈 경로의 `except`를 전부 따라가야 한다.**
> 상위 타입을 물려받는 순간 기존 포괄 처리가 그것을 삼킨다. 이번엔 두 겹이었다.

## 통과하는 테스트만으로는 확인이 안 된다

방어를 넣은 뒤 테스트 171건이 전부 통과했다. **방어를 꺼보고 나서야 의미가 생겼다.**

```
방어 없음: 유사도 1.000 반환 — 예외 없이 그냥 나온다
방어 있음: IndexDriftError — 멈춘다
```

페르소나 회귀에서 배운 것을 그대로 적용했다.
`docs/notes/persona-regression.md`의 음성 대조 절 참고.

## 남은 것 — 현업은 여기서 더 간다

찾아본 관례는 **인덱스 별칭(alias)** 방식이다.

1. 새 모델로 `index_v2`를 만들어 뒤에서 채운다
2. 별칭을 원자적으로 v2로 옮긴다 (무중단)
3. **구 인덱스를 48~72시간 남겨둔다.** 문제가 생기면 별칭만 되돌린다

**우리는 통째로 지우고 다시 넣는다**(`_replace_anchors_sync`). 앵커가 121건이라
재적재가 몇 초면 끝나서 지금은 문제가 아니지만, **롤백 수단이 없다는 것**은 사실이다.
별칭을 되돌리는 것과 전량 재색인은 다른 일이다.

- 인덱스 별칭과 무중단 전환은 안 했다
- 카나리 배포로 새 인덱스에 트래픽을 조금씩 보내는 것도 안 했다
- 도장은 컬렉션 단위다. 레코드마다 모델이 섞인 상태(lazy re-embedding)는 다루지 않는다
