# 프롬프트 캐싱 — 걸리는 조건과 이 프로젝트에서의 판단

> 측정: 2026-08-01 · `gpt-4o-mini-2024-07-18` · 같은 시스템 프롬프트로 연속 2회 호출
> 재현: 프롬프트 길이를 바꿔가며 응답의 `usage.prompt_tokens_details.cached_tokens`를 읽는다

`dev-plan.md`의 Phase 4에 "공통 프리픽스와 개인 델타를 분리해 캐싱이 걸리게 한다"를
적어뒀다. **구현하기 전에 이 계정과 모델에서 캐싱이 실제로 어떤 조건에서 걸리는지
먼저 쟀다.** 결과가 설계 전제를 바꿨다.

## 측정

| 프롬프트 | 입력 토큰 | 1회차 캐시 | 2회차 캐시 | |
|---|---|---|---|---|
| 짧은 것 | 141 | 0 | 0 | 안 걸림 |
| 중간 | 855 | 0 | 0 | **안 걸림** |
| 긴 것 | 1,485 | 0 | **1,408** | 걸림 |
| 더 긴 것 | 2,535 | **1,408** | **2,432** | 걸림 |

세 가지가 드러난다.

1. **최소 요건이 있다.** 855토큰은 안 걸리고 1,485토큰은 걸린다. 경계는 약 1,024다
2. **적중 단위가 128의 배수다.** 1,408 = 11x128, 2,432 = 19x128.
   프리픽스를 128토큰 블록 단위로 잡는다는 뜻이다
3. **프리픽스는 요청을 넘어 공유된다.** 2,535토큰 호출이 **1회차부터** 1,408을
   적중시켰다. 앞선 1,485토큰 프롬프트와 앞부분이 같았기 때문이다.
   이것이 "공통 프리픽스를 앞에 둔다"가 실제로 작동한다는 증거다

## 그런데 이 프로젝트는 캐싱이 안 걸린다

**현재 판정 프롬프트는 273토큰이다.** 최소 요건의 4분의 1에 불과하다.
페르소나 시스템 프롬프트를 붙여도 700토큰 안팎으로 예상되므로 여전히 미달이다.

## 그러면 1,024를 넘기게 늘리면 되나 — 아니다

캐시된 입력 토큰은 절반 값이다. 그 할인을 감안해도 계산이 이렇게 나온다.

| 구성 | 토큰 | 캐시율 | 100만 건 입력 비용 |
|---|---|---|---|
| **현재 (캐싱 불가)** | 273 | 0% | **40.95달러** |
| 페르소나 추가 예상 (캐싱 불가) | 700 | 0% | 105.00달러 |
| **1,024 넘기려 패딩** | 1,100 | 90% | **90.75달러** |
| 1,024 넘기려 패딩 | 1,100 | 95% | 86.62달러 |

**캐싱을 걸려고 273에서 1,100토큰으로 늘리면 비용이 2.2배가 된다.**
90% 적중이라는 낙관적 가정에서도 그렇다.

> **캐싱은 이미 긴 프롬프트의 비용을 깎는 장치이지, 캐싱을 목적으로 프롬프트를
> 늘리는 것은 손해다.** 할인율(50%)이 늘어난 토큰 양(4배)을 못 이긴다.

그리고 Phase 3.5 실측에서 확인한 것이 하나 더 걸린다. **게이트에 TPM 제어가 없다.**
프롬프트를 4배로 늘리면 같은 RPM에서 TPM 소모가 4배가 되어 429가 훨씬 빨리 온다
(`concurrency.md` 참고). 비용도 늘고 한도에도 더 빨리 부딪힌다.

## 그래서 Phase 4는 이렇게 간다

| 하는 것 | 이유 |
|---|---|
| **프리픽스와 델타를 분리한다** | 캐싱과 무관하게 구조가 낫다. 고정 지시문과 변동분이 섞이면 어느 쪽을 고쳤을 때 무엇이 달라지는지 추적이 안 된다 |
| **프리픽스에 변동 값을 넣지 않는다** | 세션 ID나 시각이 앞에 끼면 바이트가 매번 달라져 나중에 프롬프트가 자라도 캐싱이 영영 안 걸린다 |
| **캐시 적중 토큰을 계측한다** | 지금은 0이 나올 것이다. **0이라는 것을 아는 것이 목적이다** |
| **캐싱을 위해 프롬프트를 늘리지 않는다** | 위 계산 |

즉 **캐싱을 "지금 얻는 이득"이 아니라 "나중에 걸릴 수 있는 구조"로 다룬다.**
프롬프트가 자연히 자라 1,024를 넘기는 시점(few-shot 예시 추가, 규칙 확장 등)에
코드를 고치지 않고 캐싱이 걸리는 상태로 만들어 두는 것이 이번 목표다.

## 이 문서가 남기는 것

**"프롬프트 캐싱을 적용했다"가 아니다.** 안 걸리기 때문이다.

남는 것은 **적용하지 않기로 한 근거의 수치**다. 최소 1,024토큰에 128단위,
현재 판정 프롬프트 273토큰, 억지로 늘리면 2.2배 손해. 그래서 캐싱을 켜는
대신 나중에 걸릴 수 있는 구조로만 잡아뒀다. 프리픽스에 변동 값이 들어가지
않게 하는 것이 그 구조다.
