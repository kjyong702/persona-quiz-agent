# 임계값 1차 측정 결과

> 측정: 평가셋 372건 · 앵커 58건 · `text-embedding-3-small` · `norm-v1`
> 재현: `uv run python -m scripts.seed && uv run python -m scripts.measure && uv run python -m scripts.analyze --sweep`

이 프로젝트에서 **유사도 분포를 처음 실제로 본 기록**이다. 그전까지 임계값
`0.82 / 0.55 / margin 0.05`는 근거 없이 찍은 값이었고, 이 문서가 그 근거를 대체한다.

## 한 줄 요약

**임베딩 유사도만으로는 이 문제를 깨끗하게 가르지 못한다.** 정답의 최소값(0.087)이
오답의 최대값(0.926)보다 한참 아래라 두 분포가 거의 전 구간에서 겹친다.

못 가른다.

## 2. margin은 한 번도 발화하지 않았다

```
상한(0.82) 통과: 111건
그중 margin(0.05) 미달로 LLM행: 0건
```

**설계 단계에서 예측한 그대로다** (`build-log.md`의 🔵 항목 참고). `rival`은 다른
문항 앵커 중 최고값인데, 20문항의 앵커가 서로 의미적으로 떨어져 있어 한 답변이
두 문항에 동시에 가까워지는 일이 일어나지 않는다.

`_is_confident_correct` 주석이 주장하던 정당화 — "몰라요" 같은 답변이 상한을
통과하므로 margin이 필요하다 — 도 **반증됐다.** 회피성 12건의 중앙값은 0.256으로
상한 근처에도 못 온다. 애초에 하한에서 끊긴다.

> **결론: 지금 margin 장치는 코드에 있을 뿐 아무 일도 하지 않는다.**

## 3. 현재 임계값의 성적

```
upper=0.82  lower=0.55  margin=0.05
임베딩 확정 270건 (73.6%)  ·  LLM 위임 97건 (26.4%)
❌ false accept 25건   (오답을 정답으로 확정)
❌ false reject 49건   (정답을 오답으로 확정)
```

**임베딩이 혼자 확정한 270건 중 74건(27%)이 틀렸다.** 그리고 이 오류는 LLM이
고칠 기회조차 없다.

대표 사례:

| 유형 | 유사도 | 답변 |
|---|---|---|
| FA | 0.842 | "세종대왕 아닙니다" |
| FA | 0.863 | "4년마다가 아니에요" |
| FA | 0.837 | "에베레스트산이 아니라던데요" |
| FR | 0.518 | "음 이거 초등학교 때 배운 거 같은데 우리나라 수도는 서울이고..." |
| FR | 0.343 | "조선시대에 한양이라고 부르던 그 도시요" |

**부정문이 예상대로 새고 있다.** 1차 감사에서 지적됐던 그 항목이다.

## 4. 스윕 — 안전한 임계값의 대가

false accept를 0으로 만들려면 **상한을 0.94까지** 올려야 한다.

| upper | lower | LLM 위임 | FA | FR |
|---|---|---|---|---|
| 0.94 | 0.70 | 28.6% | 0 | 66 |
| 0.94 | 0.62 | 36.8% | 0 | 56 |
| **0.94** | **0.20** | **78.5%** | **0** | **4** |

**오류를 거의 없애려면 LLM 위임이 78.5%가 된다.** 하이브리드가 아끼는 호출이
21.5%로 줄어든다.

## 무엇을 배웠나

**"LLM을 언제 부르지 않을 수 있는가"에 대한 답이 처음 수치로 나왔다.
그리고 그 답은 내가 설계할 때 기대한 것보다 훨씬 작다.**

원인은 임베딩이 재는 것이 의미가 아니라 표층 유사성이기 때문이다. 이 데이터가
그걸 두 방향으로 보여준다.

- **부정문**: 뜻이 정반대인데 유사도 0.926까지 나온다. 토큰 몇 개 차이라서
- **패러프레이즈**: 뜻이 같은데 유사도 0.340이다. 겹치는 토큰이 없어서

즉 **틀린 걸 맞다고 하고 맞는 걸 틀렸다고 하는 실패가 동시에 일어난다.**
한쪽만이면 임계값 이동으로 풀 수 있는데 양쪽이라 그게 안 된다.

| B | 앵커를 늘린다 (문장형, 패러프레이즈 앵커 추가) | 정답 하단을 끌어올릴 수 있다. 앵커 관리 비용 증가 |
| C | margin 장치를 걷어낸다 | 코드가 정직해진다. 지금 아무 일도 안 하므로 |
| D | 부정 표현 감지 시 상한 경로 우회 | 규칙 기반이 섞인다 |

**B가 유망해 보인다.** 정답-표준형과 앵커2번이 전부 1.000인 것은 **앵커와 표현이
맞으면 완벽하게 잡힌다**는 뜻이라, 앵커의 표현 다양성을 늘리면 정답 하단이
올라갈 여지가 있다. 다만 그것도 재봐야 안다.

# 2차 측정 — 앵커 확충 후 (B안)

> 앵커 58 -> 121건. 답변 데이터셋은 372건 그대로.
> 기준선은 `eval/measurements.baseline.json`에 보존.

## 무엇을 바꿨나

1차 측정에서 **어떤 정답이 낮게 나왔는지**를 문항별로 뽑아 그것만 겨냥했다. 추측으로 늘리지 않았다.

| 추가한 것 | 겨냥한 실패 |
|---|---|
| 영어/원어 표기 (`Jupiter`, `Everest`, `Seoul`, `Iron`) | `Jupiter` 0.220 — 한글 음역만 있고 영문이 없었다 |
| 우회 서술 (`만 원권 지폐에 실린 임금`, `E=mc2을 발표한 물리학자`) | 패러프레이즈 0.087~0.34 |
| `정답은 X입니다` 패턴 | 0.45~0.60으로 일관되게 낮았다 |
| 짧은 정답의 조사 결합형 (`원이요`, `철이요`) | 1글자 앵커는 어미 하나에도 크게 흔들린다 |

**지킨 규칙: 서술형 앵커는 질문에 없는 정보만 담는다.**
질문 문구를 되풀이하는 서술을 앵커로 넣으면 "질문되뱉기" 오답과 구분이 안 되어
false accept를 만든다. 예를 들어 12번 문항은 질문 자체가 "산소를 운반하는 혈액 세포"라
그 표현을 앵커에 더 넣으면 안 된다.

## 예측이 틀렸다 — 그리고 그 이유가 중요하다

작업 전 예측: **"앵커를 늘리면 정답만 올라가는 게 아니라 부정문도 같이 올라간다.
`세종대왕 아닙니다`는 세종대왕을 포함하니까."**

**틀렸다. 부정문 중앙값이 0.776에서 소수점 셋째 자리까지 그대로였다.**

이유는 `similarity`가 **앵커 중 최댓값**이기 때문이다.

- `세종대왕 아닙니다`는 **이미** 짧은 앵커 `세종대왕`과 가장 가깝다.
  새로 넣은 긴 앵커들은 그보다 멀어서 **최댓값이 안 움직인다**
- `만 원짜리 지폐에 얼굴 그려져 있는 임금님요`는 기존 앵커 **전부와 멀었다**.
  새 앵커 `만 원권 지폐에 실린 임금`이 생기자 최댓값이 크게 올랐다

**즉 앵커 추가는 "아직 덮이지 않은 표현"만 끌어올리고 "이미 덮인 것"은 건드리지 않는다.**
max 연산의 성질이라 우연이 아니다. 이게 앵커 확충이 예상보다 안전한 이유다.

다만 **rival은 예측대로 올랐다** (0.347 -> 0.371). 앵커 풀이 커지면 다른 문항 앵커와
가까워질 확률도 올라가고, 이건 max가 아니라 후보 수에 좌우되기 때문이다.
지금은 폭이 작지만 문항이 늘면 이 항이 커진다.

| 유사도 | 유형 | 답변 |
|---|---|---|
| 0.926 | 부정문 | 섭씨 0도는 아니에요 |
| 0.907 | 부정문 | 왓슨과 크릭 아니에요 |
| 0.893 | margin-틀모방 | 삼 년에 한 번씩 |
| 0.892 | 부분정답 | 빨강 초록 |

**앵커로는 못 푼다.** 부정문은 정답 표현을 그대로 포함하므로 앵커를 어떻게 늘려도

## margin은 여전히 0번

상한 통과가 111 -> 131건으로 늘었는데 margin 차단은 **여전히 0건**이다.
rival이 조금 올랐지만 상한 근처까지는 한참 멀다.

# 3차 측정 — 부정 표현 라우팅 (D안)

## 무엇을 바꿨나

임베딩이 상한을 넘겨 정답을 확신하더라도 **부정 표현이 보이면 LLM으로 넘긴다.**
구현은 `app/core/negation.py`, 적용은 `judge_service.judge`.

**규칙은 판정하지 않는다. 경로만 바꾼다.** 반어법("서울 아니면 뭐예요?")이나
전언("아니라던데요")은 부정 표현을 쓰지만 정답일 수 있다. 최종 판단은 LLM이 한다.

이 설계가 정당한 이유는 **오작동의 대가가 비대칭**이기 때문이다.

| 규칙이 틀렸을 때 | 결과 |
|---|---|
| 부정문이 아닌데 발동 | LLM을 한 번 더 부른다. **비용만 늘고 정확도 손해는 없다** |
| 부정문인데 미발동 | 원래대로 돌아갈 뿐, 더 나빠지지 않는다 |

**최악의 경우가 "지금과 같음"**이다. 규칙 기반을 섞는 판단은 여기서 나왔다.

## 패턴을 데이터로 정했다

평가셋에서 실제로 상한을 넘긴 부정문을 전부 뽑아 후보 규칙을 재봤다.

| 규칙 | 상한통과 부정문 14건 중 잡음 | 정답 오작동 |
|---|---|---|
| `아니\|않\|안\|못\|없\|틀` (넓게) | 8 | **5** |
| `아니\|아냐` | 8 | 0 |
| **`아[니닙닌냐님녜]`** | **14** | **0** (실질) |

`없`, `않`, `안`을 뺀 이유는 **14번 문항 때문이다.** 질문 자체가
`소리는 어떤 환경에서 전달되지 않나요?`라 **기대 정답도 부정 표현**이다
(`공기가 없는 곳`, `진공에서는 전달되지 않습니다`). 넓게 잡으면 정답 5건이 걸린다.

## 받침 때문에 한 번 틀렸다

처음 규칙 `아니|아냐`가 6건을 놓쳤다. 원인은 한글 활용이었다.

```
"아닙니다" = 아 + 닙 + 니 + 다     <- 부분 문자열 "아니"가 없다
"아닌 것"  = 아 + 닌 + ...          <- 마찬가지
```

어간 `아니-`에 어미가 붙으면서 `니`에 받침이 들어가 **다른 음절**이 된다.
활용형을 음절 집합(`아[니닙닌냐님녜]`)으로 열거해 해결했다.

> 한국어를 문자열 규칙으로 다룰 때 반복해서 나오는 함정이다. 조사 선택(`이/가`, `은/는`),
> 어미 활용 모두 같은 원인이다. **형태소를 문자열로 다루면 받침을 반드시 따로 생각해야 한다.**

| 20건 | 56.7% | 49.6% | **44.1%** |
| 50건 | 41.1% | 30.5% | **25.1%** |

**정지 기준(FA=0, LLM 위임 50% 이하)을 FR 10건 허용으로 달성했다.**

## 남은 FA 11건 — 성격이 바뀌었다

| 유사도 | 유형 | 답변 |
|---|---|---|
| 0.893 | margin-틀모방 | 삼 년에 한 번씩 |
| 0.892 | 부분정답 | 빨강 초록 |
| 0.871 | 부분정답 | 빨강 초록 파랑 노랑 |
| 0.850 | margin-틀모방 | 적색 녹색 황색 |
| 0.839 | 규칙-나열형 | 빨강 초록 파랑이거나 빨강 노랑 파랑이요 |

부정문이 사라지고 **"정답에 가깝지만 값이 틀렸거나 개수가 안 맞는" 유형**만 남았다.
이건 부정처럼 표지가 없어서 규칙으로 잡기 어렵다. 임계값을 올리거나
LLM에 맡기는 수밖에 없다.

## margin은 여전히 0번

세 단계 내내 한 번도 발화하지 않았다. C안(제거)의 근거가 계속 쌓이고 있다.

# 4차 — margin 조건 제거 (C안)

## 결과부터

**제거 전후 숫자가 한 자리도 다르지 않다.**

```
제거 전: FA 11  FR 27  LLM 위임 32.7%
제거 후: FA 11  FR 27  LLM 위임 32.7%
```

이게 이 작업의 근거 전부다. **실행되지만 결과를 바꾼 적이 없는 코드였다.**

## 무엇을 지웠나

정답 확정 조건이 둘이었다.

```
① similarity >= upper
② similarity - rival >= min_margin      <- 지운 것
```

`rival`은 **다른 문항** 앵커 중 최고 유사도다. ②는 "이 문항 정답과 가까운 만큼
남의 문항 정답과도 가까우면 수상하다"는 2차 검문이었다.

## 왜 지웠나 — 근거 세 가지

**1. 세 단계 내내 한 번도 발화하지 않았다**

| 단계 | 상한 통과 | margin 차단 |
|---|---|---|
| A 기준선 | 111건 | **0건** |
| B 앵커확충 | 131건 | **0건** |
| B+D | 131건 | **0건** |

**2. 근거로 삼던 전제가 반증됐다**

원래 주석은 이렇게 정당화했다. *"몰라요, 네 같은 짧고 흔한 답변이 상한을 통과한다.
그런 답변은 모든 문항에 두루 가까우므로 margin으로 걸러진다."*

측정 결과 **회피성 답변(`몰라요`, `글쎄요`, `패스` 등 12건)의 유사도 중앙값은 0.256**이다.
상한 0.82 근처에도 못 온다. **하한에서 먼저 끊기므로 margin이 볼 일이 없다.**

**3. 구조적으로 발화할 수 없었다**

발화하려면 한 답변이 자기 문항 앵커와 남의 문항 앵커에 **동시에** 가까워야 한다.
그런데 20문항의 주제가 서로 멀다(수도 / 행성 / 왕 / 대양 / 올림픽 주기).
rival 중앙값이 0.371에 그친다.

흥미로운 것은 **rival 최대가 1.000**이라는 점이다. 다른 문항 정답을 그대로 쓴
답변(오답-명백 20건)이 그렇다. 그런데 그런 답변은 **자기 문항 유사도가 낮아
상한을 못 넘는다.** 결국 margin 조건에 도달조차 하지 않는다.

## 지웠지만 관측은 남긴다

**`rival_similarity`는 계속 재고 기록한다.** 판정에 쓰지 않을 뿐이다.

`scripts/analyze.py`에 `rival_watch` 절을 두어 매번 확인한다.

```
rival 분포:  중앙 0.371   95% 1.000   최대 1.000
상한(0.82) 통과 131건 중 rival이 0.05 이내로 붙은 것: 0건
-> 되살릴 근거 없음. 문제들의 주제가 서로 충분히 멀다
```

**되살릴 조건이 명확하다: 상한을 통과한 항목 중 rival이 바짝 붙는 것이 나타나면.**
그런 일은 문항이 늘어 주제가 겹칠 때 생긴다. 앵커를 58에서 121개로 늘렸을 때
rival 중앙값이 이미 0.347 -> 0.371로 움직였으므로, 규모가 커지면 실제로 올라간다.

## 왜 남겨두지 않았나

가장 큰 이유는 **거짓 안전감**이다.

코드에 조건이 있으면 읽는 사람은 "이 장치가 무언가 막아주고 있다"고 믿는다.
실제로는 아무것도 안 막고 있는데, 그 사실은 **재보기 전까지 드러나지 않는다.**
안 쓰는 코드를 남겨두는 비용이 그것이다.

> **한 줄**: 조건을 지운 게 성과가 아니라, **지워도 숫자가 안 변한다는 걸 아는 것**이 성과다.

# 5차 — 임계값 확정 (A안)

## 확정값

```
upper_threshold = 0.90
lower_threshold = 0.26
```

`config.py`와 `.env.example` 양쪽에 반영했다. **처음으로 근거가 있는 값이다.**

## 왜 이 값인가

**기준은 false accept 0건이다.** 오답을 정답으로 확정하는 것은 LLM이 고칠 기회조차
없는 오류라, LLM 호출 비용으로 살 수 있는 종류가 아니다. 그 조건에서 false reject까지
0으로 만드는 가장 싼 조합을 골랐다.

| | 값 |
|---|---|
| false accept | **0건** |
| false reject | **0건** |
| LLM 위임 | 66.8% |
| 위임 판단 정확도 | 71.0% -> **82.8%** |

**비용보다 정확도를 먼저 둔 선택이다.** LLM 위임이 32.7%에서 66.8%로 두 배가 됐다.
그 대가로 오류 38건이 0이 됐다.

## 과적합을 검증했다

**"오류 0건"은 같은 데이터로 맞춘 값이라 가장 위험한 지점이다.** 최악 사례 하나가
겨우 통과하도록 조인 값이기 때문이다. 그래서 홀드아웃으로 재봤다.

`uv run python -m scripts.analyze --holdout`

**문항 단위로 나눴다.** 무작위로 섞으면 같은 문항의 답변이 train과 test 양쪽에
들어가는데, 앵커는 문항마다 공유되므로 정보가 샌다.

```
train 문항 10개 (179건)  /  test 문항 10개 (188건)

train에서 고른 값: upper=0.90  lower=0.38
  train: FA 0  FR 0   LLM위임 58.7%
  test : FA 0  FR 2   LLM위임 53.7%    <- 처음 보는 문항
```

**읽는 법 두 가지.**

1. **상한이 일치했다.** train에서 고른 값도, 전체에서 고른 값도 `0.90`이다.
   상한은 데이터가 바뀌어도 안정적이라는 뜻이다
2. **하한은 민감했다.** `0.38`(train) vs `0.26`(전체). 그래서 **안전한 쪽인
   낮은 값을 택했다.** 하한이 낮으면 오답 확정을 덜 하고 LLM에 더 맡긴다

그리고 가장 중요한 것:

> **test에서도 FA가 0을 유지했다.** 가장 나쁜 오류 유형은 처음 보는 문항에서도
> 막힌다. 반면 **FR은 2건 생겼다.** 즉 `FR=0`은 "이 데이터에서 0"이지
> **"항상 0"이 아니다.** 이걸 아는 채로 쓰는 것과 모르고 쓰는 것은 다르다.

참고로 옛 값(`0.82 / 0.55`)을 같은 test에 적용하면 `FA 2, FR 15`가 나온다.

## 남은 것

**LLM 위임 66.8%는 하이브리드의 이득이 작다는 뜻이다.** 임베딩이 처리하는 건 33%뿐이다.
이걸 줄이려면 FR을 몇 건 받아들이거나(FR 10건 허용 시 49.3%), 임베딩 단계의
변별력 자체를 올려야 한다. 후자가 본질적인 해법이고 선택지는 조사해뒀다.

- **크로스 인코더 / NLI 모델을 임베딩과 LLM 사이에 넣는다.** 바이인코더는 두 문장을
  따로 임베딩해서 부정과 미묘한 차이를 못 잡는다. 두 문장을 함께 넣는 구조가
  그걸 잡고, 로컬 실행이라 API 비용이 없다. 검색의 retrieve -> rerank와 같은 형태다
- 한국어 특화 임베딩(KURE 등)으로 교체. 다만 **부정 문제는 구조 문제라 이걸로 안 풀린다**

이번 사이클에서는 하지 않는다. Phase 4~7이 남아 있고, **"여기까지 재봤고 다음은
이것"**이 기록으로 남아 있는 편이 낫다.
