# promptfoo 평가

```
export PROMPTFOO_PYTHON="$(pwd)/.venv/bin/python"
set -a && . ./.env && set +a
uv run python -m scripts.build_promptfoo_cases          # 케이스 생성
npx promptfoo@latest eval -c eval/promptfoo/judge.yaml  # 실행
npx promptfoo@latest view                               # 결과 브라우저로
```

## 왜 여기만 promptfoo인가

**세 가지를 재는데 도구가 갈린다.**

| 재는 것 | 도구 | 이유 |
|---|---|---|
| 임베딩 유사도 분포 | `scripts/measure.py` + `analyze.py` | 임계값을 정하려면 같은 데이터에 값만 바꿔 **수십 번** 계산해야 한다. 매번 호출하면 값이 미세하게 흔들려 0.90과 0.92를 비교할 수 없다. 한 번 재고 캐시한다 |
| **LLM 판정 프롬프트** | **promptfoo** | 프롬프트를 넣고 출력이 규칙에 맞는지 보는 일. 버전을 나란히 놓고 비교하는 것도 이 도구가 한다 |
| **페르소나 진행 멘트** | **promptfoo** | 위와 같음 |

**임베딩 측정을 promptfoo로 옮기면 오히려 나빠진다.** 도구 선택이 아니라 재현성 문제다.

## 프롬프트를 베끼지 않는다

`judge_prompt.py`가 `app.core.prompts.load`와 `app.core.llm.build_user_message`를
**그대로 부른다.** 평가용으로 프롬프트를 복사해두면 운영을 고쳤을 때 평가가 옛 버전을
계속 재고 아무도 모른다. **평가는 통과하는데 서비스는 달라져 있는 상태**가 가장 나쁘다.

`assert`의 `transform`도 `llm.parse_verdict`와 **같은 순서**로 본다.
`incorrect`를 먼저 검사해야 한다. `correct`로 먼저 보면 `incorrect`가 `correct`를
포함해서 오답이 정답으로 뒤집힌다. 운영 코드에서 겪은 함정이 평가에서도 그대로 나온다.

## 무엇을 재는가

전체 372건이 아니라 **LLM 위임 경로 266건**이다. 운영에서 LLM 판정을 받는 답변은
임계값 사이에 떨어진 것들뿐이라, 전체를 재면 프롬프트 성능은 알 수 있어도
**이 시스템이 실제로 얼마나 맞히는지**는 안 나온다.

> **임계값을 옮기면 대상도 바뀐다.** `scripts/build_promptfoo_cases.py`를 다시 돌려야 한다.

## 결과 — 판정 프롬프트 v1 -> v3

| 버전 | 통과 | 정확도 | FA | FR |
|---|---|---|---|---|
| judge.v1 | 251/266 | 94.4% | **4** | 11 |
| judge.v2 | 258/266 | 97.0% | 3 | 5 |
| **judge.v3** | **259/266** | **97.4%** | **1** | **6** |

수치는 `summary-judge.json`. 원본은 7MB가 넘어 커밋하지 않는다
(`scripts/summarize_promptfoo.py`가 줄인다).

**가장 중요한 것은 FA 4 -> 1이다.** 오답을 정답으로 확정하는 오류는 되돌릴 기회가 없다.

### v1이 틀린 이유는 두 종류였다

**① 규칙이 아예 없던 것** (FA 4건 전부)

| 실패 | v1에 규칙 |
|---|---|
| `대한민국의 수도요` (질문 되뱉기) | 없음 |
| `산소를 운반하는 혈액 세포요` | 없음 |
| `왓슨` (두 명을 물었는데 한 명) | 없음 |
| `왓슨과 크릭 아니에요` (부정) | 없음 |

**② 규칙은 있는데 좁게 읽힌 것** (FR)

v1에 `맞춤법, 띄어쓰기, 조사, 존댓말 차이는 무시한다`가 있는데도
`목셩`, `테평양`, `에레베스트산`, `아인쉬타인`이 전부 오답 처리됐다.
**모델이 "맞춤법"을 좁게 읽어 자판 오타까지는 포함하지 않았다.**
v2에서 `오타`와 `글자가 한두 개 틀렸거나 자판을 잘못 눌러도`를 명시하자 풀렸다.

> **규칙을 썼다고 지켜지는 것이 아니다.** 어떤 말로 썼는지가 결과를 가른다.

### v2가 새로 깨뜨린 것 — 규칙의 과발화

v2에서 넣은 `답을 하나 제출했다면 자신 없다는 말을 덧붙여도 정답이다`가
**답을 언급했다가 철회한 답변까지 정답으로 만들었다.**

```
"세종대왕이었나 아 모르겠어요 패스할게요"   -> v2가 정답 처리 (라벨은 오답)
```

v3에서 `답을 말했다가 철회하거나 답하지 않겠다고 하면 오답이다`를 더해 갈랐다.

> **규칙을 하나 넣으면 다른 데가 깨지는지 봐야 한다.** 평가셋이 없으면 이 사실을
> 알 방법이 없다. 프롬프트를 고칠 때마다 전체를 다시 도는 것이 평가 도구의 값이다.

## temperature=0인데 결정적이지 않다

같은 프롬프트로 세 번 돌렸다.

```
judge.v3 · temperature=0 · 266건 × 3회
  회차별 통과: 259, 260, 259
  결과가 흔들린 케이스: 1건 (0.4%)
```

`summary-determinism.json`. **흔들리는 케이스는 요약에서 `flaky`로 따로 센다.**
한 번 틀렸다고 실패로 세면 노이즈가 성적에 섞인다.

흔들린 것은 `태양에서 다섯 번째로 떨어져 있는 가스로 된 행성이요`.
**처음에는 이 케이스를 "v3가 깨뜨렸다"고 읽었는데 재보니 노이즈였다.**

`temperature=0`은 매 스텝 최고 확률 토큰을 고르라는 뜻이지 **연산이 매번
비트 단위로 같다는 뜻이 아니다.** 부동소수점 누적 순서, 배치 구성, 라우팅이
달라지면 최상위 두 토큰의 확률이 붙어 있을 때 순위가 뒤집힌다.

**그래서 1~2건 차이는 개선이라고 부를 수 없다.** v2와 v3의 차이가 정확히
그 크기다. **v3를 고른 근거는 총점이 아니라 FA가 3에서 1로 준 것과,
과발화한 규칙을 논리적으로 갈랐다는 것이다.**

## 세 버전 모두 실패한 6건

프롬프트로는 못 푸는 자리다.

| 답변 | 라벨 | 성격 |
|---|---|---|
| `조선 4대 임금이요` | correct | 우회 서술을 모델이 안 받아들인다 |
| `한국이랑 미국 사이에 있는 바다요` | correct | 같음 |
| `저혈구` | correct | 오타인데 `백혈구`와 헷갈릴 여지가 있다 |
| `왓슨` | incorrect | 두 명 중 한 명. 규칙을 넣어도 안 잡힌다 |
| `왓슨, 크릭, 그리고 로절린드 프랭클린` | correct | **라벨이 논쟁적**. 질문은 "두 과학자"인데 셋을 답했다 |
| `37도` | correct | **라벨이 논쟁적**. 기대 정답은 36.5도, `36도에서 37도 사이`도 있다 |

**뒤 둘은 프롬프트 문제가 아니라 라벨 문제다.** 데이터셋의 `rationale`에
"판단이 갈린다"고 이미 적혀 있는 경계 탐침이다.

> **평가 결과가 나쁘면 프롬프트만 의심하면 안 된다.** 라벨이 틀렸을 수 있고,
> 애초에 사람도 갈리는 문제일 수 있다. 이 6건 중 2건이 그렇다.

## 남은 것

- **프롬프트를 이 평가셋에 두 번 맞췄다. 과적합 위험이 있다.** 임계값 때는 문항 단위
  홀드아웃으로 검증했는데 프롬프트는 아직 안 했다. 다만 고친 것이 예시가 아니라
  규칙이라 덜 위험하다고 본다
- 사람 검수 대기 113건. 라벨이 뒤집히면 위 수치가 바뀐다
- 흔들림 폭을 알려면 반복 횟수를 늘려야 한다. 3회로는 0.4%가 상한인지 모른다
